# Requirements — 产品橱窗 Dashboard（完整能力展示 + 数字员工训练成长 UI）

> Spec ID: `product-showcase-dashboard`
> 状态: Draft（待评审）
> 上游依赖: `console-experience-byo-model`（BYO 模型路径与模型来源徽标；可并行开发，合流时消费其 `communityModelSource` 查询）
> 定位宣言: 社区版前端从"治理演示控制台"升级为**产品橱窗**——访客在一个界面里看到平台的完整能力地图，可用的真实可跑，商业版的诚实标注并成为升级引导。其中"训练数字员工"是本 spec 的旗舰展示面。

---

## 1. 背景与动机

GitHub 案例研究（2026-08-18）结论：开源项目的演示面就是营销漏斗。当前社区版有两个前端面，都没有承担"产品橱窗"职责：

1. `/console`（后端静态单页）——只演示治理闭环，访客看不到平台能力全貌，"没有 AI 模型配置""没有员工管理""没有训练"成为第一印象误读。
2. `packages/dashboard`（React Governance Dashboard）——只有运行/执行/审批三个运维视图，信息架构是"工具"而非"产品"。

用户决策（2026-08-18）：**UI 至少把功能完整地显示给用户看，训练员工的 UI 作为产品橱窗**。即：产品能力全景 + 数字员工训练成长界面，是社区版转化漏斗的核心投资。

对标锚点：Dify（产品级自托管演示驱动 100k+ stars）、Langfuse（"值得截图"的开源界面即最便宜的营销）。商业能力在开源侧的呈现方式采用"诚实预览 + 升级引导"（open-core 标准玩法），不假装修、不遮挡。

## 2. 现状锚点（改造对象）

| 组件 | 位置 | 现状 |
|---|---|---|
| React Dashboard | `packages/dashboard/src/`（App + 3 views，共 ~730 行） | 顶部 tabs：run / executions / approvals；轮询 feed；本地 i18n map（zh/en） |
| GraphQL 演示面 | `packages/backend/src/community/runtime/community-agent-runtime.resolver.ts` | `communityAgents { id name status }`；执行/审批/事件查询（见 spec1 §2） |
| 种子员工 | `community-demo-seed.service.ts` | 单员工 Follow-up Assistant：`description / prompt / guardrailRules.sensitiveOps`（L1 `audit` 放行、L3 `approve` 暂停）真实在库 |
| 审批数据 | approval instances | 决定带 `comment`（审批意见），已持久化——**训练反馈的现成数据源** |
| 重放能力 | `communityExecuteAgent` mutation | 以 `rawInput` 重新提交即重放，确定性场景可复现——**零新 mutation** |
| i18n 纪律 | dashboard 本地 `i18n.ts`；shared locales 有 200 行上限 | 橱窗文案放 dashboard 本地 map，不触碰 shared 上限 |

## 3. 用户故事与验收标准（EARS）

### US-4 产品橱窗信息架构（访客）

**US-4** 作为第一次接触 NexusClaw 的访客，我希望在一个界面里看到平台能力的完整地图，以便判断这个产品的全貌与边界。

- **AC-4.1 产品级外壳**：当进入 Dashboard 时，系统应当呈现产品级布局——左侧导航分区 + 顶部工作区状态栏（模型来源徽标、待办角标、语言切换），替代现有顶部 tabs。
- **AC-4.2 能力全景**：导航应当按平台能力域组织（概览 / 数字员工 / 运行 / 审批 / 审计链 / 训练成长 / 治理策略 / 完整产品能力），社区版可用的分区进入功能页。
- **AC-4.3 商业版诚实预览**：当访客浏览商业版专属能力（可视化构建器、深度成长回路、模型路由、企业模块等）时，系统应当展示预览卡（能力说明 + 官网链接 + "商业版"徽标），不提供任何假装可用的交互。
- **AC-4.4 概览页**：当进入概览分区时，系统应当聚合展示执行总数、待审批数、治理事件、模型来源与快速入口（跑一次闭环 / 处理审批），数据来自现有查询的前端聚合。
- **AC-4.5 空状态引导**：当任一分区无数据时，系统应当展示引导性空状态（说明该区做什么 + 下一步动作入口），不展示裸空白。

### US-5 数字员工管理展示（评估者）

**US-5** 作为评估"AI 数字员工平台"能力的访客，我希望看到员工列表与员工详情画像，以便理解数字员工在平台中如何被定义、约束和观察。

- **AC-5.1 员工卡片墙**：当进入数字员工分区时，系统应当以卡片墙展示每个员工（头像、名称、状态、职责描述、关键统计：执行数 / 审批通过率 / L3 触发数）。
- **AC-5.2 员工详情页**：当点击员工卡片时，系统应当展示详情页——画像（description + prompt 只读）、治理策略（guardrailRules 渲染，链接到治理策略分区）、最近执行列表、成长记录入口。
- **AC-5.3 数据真实性**：员工统计与详情应当全部来自运行时真实数据（seed + 用户操作产生），禁止前端伪造演示数字。
- **AC-5.4 后端读模型**：`communityAgents` 应当扩展统计字段，并新增员工详情聚合查询（画像 / 策略 / 最近执行 / 成长时间轴），全部只读、无新表。

### US-6 训练成长 UI——训练员工（旗舰展示面）

**US-6** 作为想理解"数字员工如何被训练和改进"的访客，我希望看到一个真实可用的训练成长界面，以便体会治理数据如何转化为员工的成长记录。

- **AC-6.1 成长时间轴**：当进入训练成长分区时，系统应当按员工展示成长时间轴——每条审批决定（批准 / 拒绝 + 审批意见）、每次 L3 升级暂停、每次执行完成，都应当以辅导记录 / 里程碑节点呈现，并回链到对应执行。
- **AC-6.2 审批即训练**：当审批人提交拒绝决定并填写意见时，该意见应当作为辅导笔记出现在该员工的成长时间轴上（数据派生自 approval instances，非新采集）。
- **AC-6.3 重放对比（训练复盘）**：当用户在某条成长记录上选择"重放训练"时，系统应当以原 `rawInput` 重新提交执行，并在完成后并排对比两次执行的步骤差异与结果。
- **AC-6.4 能力雷达 / 统计卡**：员工详情应当展示从审计链真实计算的统计（执行成功率、审批通过率、L3 触发率、平均耗时），标注数据来源为审计链。
- **AC-6.5 成长种子**：首次启动的种子数据应当包含 2–3 条历史辅导记录（幂等 seed，固定 UUID），保证橱窗不空。
- **AC-6.6 商业边界诚实**：深度成长回路（模型微调、范例库、自动化成长）应当以"商业版"预览卡呈现在训练成长分区内，明确说明社区版展示的是治理数据派生的成长视图，不伪造微调能力。

### US-7 治理策略可视化（评估者）

**US-7** 作为关心治理能力的评估者，我希望直观看每个员工的权限与风险策略，以便理解 deny-by-default 与 L0–L4 分级如何落地。

- **AC-7.1 策略表**：治理策略分区应当以表格渲染 seeded `sensitiveOps`（工具 / 操作 / 风险级 / 动作 / 说明），风险级与动作以语义芯片呈现。
- **AC-7.2 只读边界**：策略页应当为只读展示（编辑能力属商业版，以预览卡标注），并附 deny-by-default 一段说明文案。

### US-8 壳、入口与互链（访客 / 维护者）

**US-8** 作为自托管用户，我希望一条路径就能打开产品橱窗，并与零依赖演示控制台互相跳转。

- **AC-8.1 生产可达**：Dashboard 构建产物应当在生产 compose 栈中可达（backend 静态托管或独立服务，实现取其一），路径与端口在 README 说明。
- **AC-8.2 互链**：`/console` 头部应当提供"打开产品橱窗"链接；Dashboard 应当提供"零依赖演示控制台"链接。
- **AC-8.3 文档**：README（EN + 中文）快速开始应当把 Dashboard 作为主入口介绍，`/console` 定位为零依赖快速演示。

### US-9 快照纪律（维护者，继承 spec1 US-3）

**US-9** 作为项目维护者，我希望橱窗改造不破坏社区版边界与门禁。

- **AC-9.1 零新依赖**：Dashboard 不新增 npm 依赖（无 UI 组件库 / 图标库；图标用内联 SVG；样式手写 CSS 设计系统，与 spec1 令牌语言一致）。
- **AC-9.2 命名纪律**：新增代码路径与标识符不得命中 `check-community-boundary.mjs` 的 banned pattern（规避 workforce / employee-package / ai-workforce-learning 等词汇；成长相关命名使用 `agent-growth` / `coaching` 语义）。
- **AC-9.3 门禁保持**：`npm run build` / `check:i18n` / `check:boundary` / 全部测试套件应当继续通过；`packages/shared` 零改动（dashboard i18n 本地化）。
- **AC-9.4 测试覆盖**：成长时间轴派生规则、员工统计聚合 resolver、重放对比交互、i18n zh/en 键奇偶、空状态与预览卡渲染，均应当有自动化测试。
- **AC-9.5 i18n 完整性**：新增界面字符串应当全部进入 dashboard 本地 i18n map 的 zh/en 两表（键集合相等进入测试）。

## 4. 非目标（明确不做）

- 不实现商业版成长回路本体（微调、范例库、自动策略调优）——只做治理数据派生的成长视图 + 诚实预览卡。
- 不做员工创建 / 编辑 / 发布流（agent-builder 属商业版）；员工详情只读。
- 不做模型管理界面（spec1 已限定 BYO 为环境变量级）。
- 不引入路由库 / 状态库 / UI 组件库（零新依赖纪律）。
- 不改 `/console` 的零依赖单文件形态（spec1 负责）。

## 5. 依赖与风险

| 风险 | 缓解 |
|---|---|
| 范围蔓延成"重写商业版" | 非目标清单 + 商业能力一律预览卡化；每个分区先读模型后 UI |
| 伪造感（假数据假功能）反噬信任 | AC-5.3 / AC-6.4 数据真实性红线：统计只从审计链计算；预览卡不假装修可用 |
| 单数据源稀疏（一个员工、少数执行）导致橱窗冷清 | AC-6.5 幂等成长种子；员工卡片墙预留多员工布局（seed 结构已支持多 insert） |
| 手写 CSS 视觉投入失控 | 复用 spec1 设计令牌语言；两 spec 共享令牌命名，避免两套审美 |
| 命名误触商业词汇禁则 | AC-9.2 + `check:boundary` 进收尾门禁 |
