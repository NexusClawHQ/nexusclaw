# Requirements — 橱窗视觉精修与全端统一（mockup 驱动）

> Spec ID: `showcase-visual-refinement`
> 状态: **Draft — Mockup 评审中**（本 spec 的第一交付物是 mockup，评审通过后才进入实现）
> 上游依赖: `product-showcase-dashboard`（G–L 已实现，本 spec 是其视觉层的精修与统一）
> 定位宣言: 用户已给出商业产品界面参考图，并确认四条视觉决策——**浅色白底、产品级框架与边距节奏、完整能力展示、商业功能点击弹说明**。本 spec 把这四条收敛成**单一设计令牌系统**与**逐页 mockup 基线**，先评审、后实现。

---

## 1. 背景与反馈链

视觉问题经过四轮用户反馈逐步聚焦：

1. 「界面怎么会那么丑」→ 深色 GitHub 运维风不适合产品橱窗定位；
2. 「不要使用深色，使用白色」→ 全局切浅色；
3. 「系统框架、组件边距实在太丑，参考附件产品界面」→ 间距节奏与框架密度是核心痛点；
4. 「把这个页面完全开源，商业功能点击后显示商业版功能」→ 产品控制台形态确认。

当前状态：外壳（顶栏/分组侧栏/产品控制台/概览）已按参考语言重做并部署；**员工详情、训练成长、治理策略、审批、审计链五个内页仍沿用第一版 panel 体系，未逐页精修**；console 与 dashboard 两套 CSS 令牌近似但独立。本 spec 补齐这两块，并把「先看效果再写码」固化成流程。

## 2. Mockup 评审流程（本 spec 的差异化机制）

```
[本 spec] assets/mockup/index.html（单文件、零依赖、可交互切页、含设计标注开关）
        │  ① 用户浏览器打开评审（file:// 或 python -m http.server）
        │  ② 逐页标注修改意见 → 更新 mockup → 再评审，直至拍板
        ▼  ③ mockup 冻结 = 视觉基线（设计令牌 + 逐页布局结构）
实现阶段（tasks.md Phase M–P）以冻结 mockup 为验收对照
        │  ④ 偏差容忍度：布局结构必须一致；间距/字号允许 ±4px 级微差
        ▼
回归门禁（guard 测试断言令牌一致性，见 AC-5.4）
```

Mockup 是设计工件不是产品代码：允许内联演示数据与少量切换脚本，不进构建链、不影响 `/app` 与 `/console`。

## 3. 用户故事与验收标准（EARS）

### US-1 单一设计令牌系统（开发者/维护者）

- **AC-1.1 令牌单一来源**：设计令牌（色彩/间距/圆角/阴影/字号/层级）应当定义于 design.md §2 的令牌表，并由 mockup 完整示例化；dashboard 与 console 的实现各自映射该表，值偏差为零（关键令牌）或 ±1px 色阶（衍生色）。
- **AC-1.2 布局网格统一**：两端的侧栏宽度、顶栏高度、内容区最大宽度、卡片内边距、分区间距应当取同一组常量（design.md §3 网格表）。
- **AC-1.3 组件语言统一**：芯片、按钮、JSON 代码块、空态、时间轴节点在两端应当共享同一视觉规格（尺寸/配色/圆角/描边）。

### US-2 逐页视觉精修（访客）

- **AC-2.1 Mockup 全覆盖**：mockup 应当覆盖全部九个界面——登录、概览、数字员工墙、员工详情、训练成长、审批、审计链、治理策略、产品控制台（含商业弹窗打开态）——每页以真实演示场景的中文文案与数据呈现。
- **AC-2.2 实现一致性**：实现后的每个分区，其布局结构（区块顺序/层级/组件形态）应当与冻结 mockup 对应页一致；偏差超出容忍度视为未完成。
- **AC-2.3 内页精修范围**：员工详情、训练成长、治理策略、审批、审计链五个内页应当按新设计系统重排（此为当前未完成的主要工作量）。
- **AC-2.4 响应式基线**：mockup 与实现应当在 860px 断点提供侧栏折叠为横滑条的单列降级，在 1280px 以上保持内容区最大宽度约束。

### US-3 设计标注（评审者）

- **AC-3.1 标注开关**：mockup 应当提供「设计标注」开关；开启后在关键区域（侧栏宽度、卡片内边距、分区间距、字号层级、令牌色板）叠加标注层，展示对应令牌名与值。
- **AC-3.2 令牌色板页**：mockup 应当包含完整令牌色板页（design tokens swatches），作为 AC-1.1 的可视化对照。

### US-4 console 对齐（访客/维护者）

- **AC-4.1 视觉对齐**：console 的令牌命名与取值应当迁移到统一令牌表；迁移后 `/console` 视觉与 dashboard 同语言（允许 console 因单文件形态保留简化实现，但值必须同源）。
- **AC-4.2 守卫延续**：console 现有守卫（零外部资源、textContent-only、COPY 奇偶、稳定状态键）应当全部保持通过。

### US-5 纪律延续（维护者）

- **AC-5.1 零新依赖**：视觉精修不引入任何 npm 依赖与外部资源；图标保持内联 SVG。
- **AC-5.2 令牌守卫测试**：应当新增守卫测试，断言两端 CSS 中关键令牌（背景/面板/品牌色/圆角/间距基线）值一致，防止后续漂移。
- **AC-5.3 i18n 与可达性延续**：新增/改动文案全部走 i18n 双表；交互控件保持键盘可达与 aria 标注。
- **AC-5.4 门禁保持**：`npm run build`、`check:i18n`、`check:boundary`、两端测试套件全部保持通过。

## 4. 非目标（明确不做）

- 不做商业产品界面的像素级复刻——参考图定义**语言与密度**，不定义像素规格；
- 不改任何后端逻辑与 GraphQL 契约（纯视觉层 spec）；
- 不引入路由库/组件库/图标库/CSS 框架；
- 不做主题切换（浅色是唯一主题）；
- mockup 不进入 `/app` `/console` 的构建产物。

## 5. 依赖与风险

| 风险 | 缓解 |
|---|---|
| 参考图只读出布局语言，像素意图误读 | mockup 评审循环（§2）在写码前消除误解 |
| 两端 CSS 同步漂移 | AC-5.2 令牌守卫测试进 CI |
| 精修范围蔓延成重构 | 非目标清单 + 每页只动布局结构与样式，不动数据流 |
| mockup 与实现长期失养 | mockup 冻结后仅随视觉决策变更而更新，并在 tasks 中列为显式任务 |
